# Приёмка Horar v2.0.1 — Safari, архивы и интерфейс

**Область:** интеграция MethodCorrectionEvidence v2.0.1 с браузерным Horar v2.5.
**Основание:** CORRECTIVE_2_0_1.md, tests/corrections.test.mjs, tests/corrective-integration.test.mjs.
**Важно:** автоматические тесты подтверждают реализацию контрактов, но не астрологическую предсказательную достоверность.

## Подготовка

1. Экспортировать существующую базу Horar в JSON и сохранить оригинал отдельно. Не использовать рабочую базу для разрушительных испытаний.
2. Взять сборку именно ветки \`qa/v2-0-1-integration-acceptance\` (или её PR preview), а не старую статическую ссылку, закреплённую на прежнем коммите. Публикация нового сайта и изменение адреса НЕ входят в этот PR.
3. Для воспроизводимого локального запуска: \`npm ci && npm run dev\`; затем открыть адрес Vite. Повторить основные шаги на iPhone Safari.
4. Зафиксировать адрес страницы (origin), версию iOS, браузер, SHA проверяемого коммита и время тестирования. LocalStorage из разных origin не разделяется.

## M-01. Секта на горизонте

Контрольный пример из независимых эфемерид: Лондон, 51.5074° N, -0.1278° E, **2025-01-01 08:12:57 UTC** (местное смещение +00:00); система Региомонтануса, \`frawley_early\`. Использовать учебный вопрос, который не содержит реальных персональных данных.

**Ожидается:** новый раздел «КОРРЕКЦИЯ МЕТОДА · 2.0.1» виден; секта не определена; обитель, экзальтация, терм, фас, изгнание и падение присутствуют; у триплицитета указаны варианты или инвариантный владелец; нет итоговых YES/NO/TIMING. Проверить, что интерфейс не содержит \`undefined\` и \`NaN\`.

## M-02. Старый архив и история ревизий

На отдельном тестовом origin/профиле импортировать архив прежней версии без \`evidence.method_correction\`. Записать хэш и позиции семи планет из исходного JSON и сравнить после импорта.

**Ожидается:** карта, момент вопроса, семь планет, дома, исходный \`source_chart_hash\` и история ревизий сохранены; новый корректирующий слой рассчитан заново; при повторном импорте нет дублей и скрытого изменения текста вопроса. Импортированные экспертные заключения не становятся подтверждёнными автоматически.

## M-03. Ошибка входных данных и атомарность

Создать тестовую копию архива, содержащую ошибочную широту \`65.0001\` (или подменённый \`source_chart_hash\`). Не редактировать основной архив.

**Ожидается:** понятное сообщение об ошибке; существующие записи в Safari не исчезают; старое состояние LocalStorage неизменно; исправление широты выполняется только вручную, не автоматическим округлением.

## M-04. Целостность интерфейса

Проверить существующие вопросы о контактах, отношениях и работе. Открыть старый вопрос, перейти к новой ревизии, вернуться к предыдущей, экспортировать и импортировать.

**Ожидается:** темы не смешиваются; прежняя карта не пересчитывается задним числом; новые свидетельства не превращаются в утверждённый прогноз; вспомогательные данные v2.0.1 не заменяют исторический контракт v1.1.

## M-05. Отрицательная проверка вердикта

Для карты с видимым прямым аспектом/антисом проверить экспертный блок и экспортированный JSON.

**Ожидается:** \`can_issue_event_verdict=false\`, \`final_prediction=null\`, \`timing_prediction=null\`; наличие геометрического кандидата не означает состоявшееся событие. Если поиск имеет технический предел, статус остаётся \`SEARCH_INCOMPLETE\`.

## Протокол результата

Для каждого M-01…M-05 указать: **PASS / FAIL / BLOCKED**, устройство, URL и commit SHA, шаги, ожидаемый/фактический результат, видео или снимок экрана. Зафиксировать отдельно недостатки отображения и численные расхождения.

**Условия приёмки:** CI зелёный, нет P0/P1 регрессий, M-01…M-05 выполнены или явно задокументированы как BLOCKED. Нельзя объявлять ручную приёмку завершённой по результатам одного CI.
